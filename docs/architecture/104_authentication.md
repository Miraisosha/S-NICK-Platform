# 認証・権限

## 位置づけ

本書は、Squash Platformの認証、セッションおよび認可に関する横断的な設計方針を整理する。利用者・ロールごとの業務要件は[利用者・権限](../specifications/9000_common/9010_user_roles.md)を正本とし、機能の詳細は[一般](../specifications/1000_public/README.md)、[運営者](../specifications/2000_operator/README.md)、[選手](../specifications/3000_player/README.md)、[管理者](../specifications/4000_admin/README.md)の各仕様を参照する。

## 認証区分

| 認証区分 | 認証 | 認証元 | 主な利用者 | 方針 | 実装状態 |
|---|---|---|---|---|---|
| 一般 | 不要 | なし | 観客、未ログイン利用者 | 公開済み情報を参照する。未ログインでの問い合わせ送信可否は検討中 | FRONT未実装 |
| 運営者 | 必要 | `users` | イベント所有者、運営スタッフ、マーカー | イベント単位のロールと担当範囲で認可する | 認証を実装済み、認可は機能ごとに実装中 |
| 選手 | 必要 | `users` | ユーザーアカウントと関連付いた選手 | 本人の申込、プロフィールおよび参加情報を対象に認可する | 未実装 |
| 管理者 | 必要 | `admins` | プラットフォーム管理者、スーパー管理者 | 運営者・選手と認証元およびセッション内の認証情報を分離する | 認証を実装済み、Cookie分離は未実装 |

運営者と選手は`users`の共通アカウントを使用する。同じ利用者がイベントを運営しながら選手として参加する場合も、アカウントを重複作成せず、対象イベントとの関係と操作内容によって認可する。大会へ登録された選手を表す`PLAYER`とログイン可能な`USER`の関連は任意であり、すべての参加選手がログインアカウントを持つ前提にはしない。マーカーは独立した認証区分にはせず、運営者区分のイベントロールとして扱う。

同じ人物が管理者と運営者または選手を兼ねる場合は、`admins`の管理者アカウントと`users`のアカウントを分ける。管理者権限を`users`のイベントロールとして付与しない。

## 認証方針と実装状態

| 項目 | 決定済みの方針 | 実装状態 |
|---|---|---|
| 運営者・選手のログイン | 確認済みメールアドレスを使用し、内部IDをログイン識別子にしない | 運営者向けを実装済み。選手向け画面は未実装 |
| 管理者のログイン | 管理者専用アカウントを使用する | 手動作成した有効な管理者によるログインを実装済み。メール確認は使用していない |
| パスワード保存 | Argon2idでハッシュ化し、平文または復号可能な形式で保存しない | `users`・`admins`とも実装済み |
| パスワード規則 | 最小8文字、最大64文字とし、特定の文字種の組合せを必須にしない。頻出・漏えいパスワードを禁止し、パスワードマネージャー、自動入力および貼り付けを許可する | 最小長は現在6文字。8文字への変更と頻出・漏えいパスワードの禁止リストは未実装 |
| 確認・再設定トークン | 本体を保存せず、SHA-256ハッシュを保存する | `users`向けを実装済み。管理者向け再設定は未実装 |
| ログイン失敗制御 | `users`は5回連続失敗で30分停止し、接続元単位のレート制限を併用する | アカウント単位の停止は実装済み。接続元単位の制限は未実装 |
| 通常セッション | 最後の利用者操作から9時間で無操作タイムアウトとする | 未実装。現在はPHPの既定セッション設定を使用 |
| 自動ログイン | 利用者が明示的に登録した信頼済み端末に取消可能なトークンを使用し、有効期間を30日とする。端末種別だけでパスワードを省略しない | 未実装 |
| パスキー | WebAuthnに準拠し、登録済みパスキーによるパスワードレス認証を導入候補とする。生体情報そのものは本システムへ送信・保存しない | 未実装。登録・復旧方法は検討中 |
| パスワード再設定後の失効 | 対象`users`アカウントの全端末セッションと自動ログインを無効化する | セキュリティスタンプによるセッション失効を実装済み。自動ログインは未実装 |
| 複数端末 | 同一`users`アカウントの有効な端末セッションを最大5件とする | 端末セッションの保存・一覧・個別失効を含め未実装 |
| 管理者の分離 | 運営者・選手と認証元、セッション、Cookie、自動ログインおよび再設定トークンを共有しない | `admins`とセッションキー`AdminAuth`の分離は実装済み。PHPセッションCookieは共通 |

## 認可

認可はURLや画面の表示だけに依存せず、APIで操作ごとに検証する。

1. 認証区分を確認する。
2. 対象イベントとの関係を確認する。
3. 固定ロールで操作種別を確認する。
4. 開催日、コート、カテゴリ、時間帯等の担当範囲を確認する。
5. 所有者限定操作や結果訂正等の追加条件を確認する。

権限は最小権限を基本とし、重要操作では操作者、日時、対象、変更前後の値を監査履歴へ記録する。

認可は機能ごとに実装中である。画面を非表示にするだけでは認可済みとせず、各APIで対象データとの関係、ロールおよび担当範囲を検証する。

業務操作ごとの許可、追加条件および明示的な禁止は[権限マトリクス](../specifications/9000_common/9402_authorization_matrix.md)を正本とする。画面・API・入力項目の確定に合わせてマトリクスを詳細化し、Policyと拒否系テストへ対応付ける。

## Cookie・CORS・CSRF

### 現在の実装

- APIは環境別の許可リストと完全一致するOriginにだけCORSレスポンスヘッダーを付与する。
- セッション内の認証情報は、運営者・選手を`Auth`、管理者を`AdminAuth`として分離している。
- 運営者・選手と管理者は、現在は同じPHPセッションCookieを使用する。
- セッションCookieの`SameSite`は`Lax`である。`Domain`は環境変数で設定できる。
- CakePHPのCSRF MiddlewareはHTML画面へ適用しているが、`/api/*`は検査対象外である。
- 現在のCORS Middlewareは許可外OriginへCORSレスポンスヘッダーを付けないが、リクエスト自体を拒否しない。

### 本番導入前に必要な対応

- Cookieを使用するAPI呼び出しをHTTPSに限定し、セッションCookieの`Secure`と`HttpOnly`を有効にする。
- 管理者用Cookieを運営者・選手用Cookieから分離する。
- APIの状態変更リクエストでは、許可外Originをサーバー側で拒否する。
- APIで受け付けるContent-Typeを制限し、CSRFトークンまたは同等の対策を組み合わせる。具体的な方式は検討中とする。
- 親ドメイン全体へCookieを共有する必要性を確認し、可能であればAPIホスト限定Cookieを使用する。
- FRONTのJavaScriptからセッションCookieの内容を直接参照しない。

CORSレスポンスヘッダーと`SameSite=Lax`だけをCSRF対策の完了とは扱わない。

## 二要素認証

二要素認証は導入方針とするが、2026年8月26日時点では未実装である。端末種別だけで適用を免除せず、スマートフォンやタブレットの入力軽減には登録済みパスキーまたは取消可能な信頼済み端末を使用する。管理者への必須化方式と導入フェーズは検討中である。

## 検討中

- 運営者・選手と管理者それぞれのセッションCookie名、最大継続時間および失効方式

- 二要素認証の方式、復旧手段および必須化範囲
- パスキーの登録・削除、同期、端末紛失時の復旧および未対応環境の代替手段
- 重要操作で再認証を要求する範囲と再認証方式
- CORS許可オリジンの環境別管理方法
- APIごとの権限表と監査対象
- 管理者アカウントの発行・停止・復旧手順
- 管理者ログインの失敗回数制限、接続元単位のレート制限および監査方法
- 管理者のパスワード再設定方法
