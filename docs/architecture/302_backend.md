# バックエンド

## 位置づけ

本書は、CakePHPバックエンドの責務、処理境界および実装状態を定義する。ディレクトリの正本は[ディレクトリ構成](102_directory-structure.md)、HTTPインターフェースは[API](303_api.md)、業務処理のクラス候補は[クラス設計](304_class_design.md)を参照する。

- 確認時点：2026年8月29日

## 現在の実装状況

PHP 8.5を開発・CI・本番の統一バージョンとして使用する。CakePHP 5.4とCakePHP Authentication 4系を使用し、`/api/v1/...`のJSON APIはHTTPメソッドを含めて明示的にルーティングする。CakePHPのフォールバックルートはAPIへ使用しない。

現在のDockerおよびCIはPHP 8.5を使用しているが、`composer.json`のPHP要件は`>=8.2`のままである。PHP 8.5を正式な実行条件として依存関係の解決時にも保証できるよう、ComposerのPHP要件を実装変更時にPHP 8.5へ合わせる。

| 領域 | 現在の実装 | 状態 |
|---|---|---|
| 通常ユーザー認証 | 登録、メール確認、ログイン、ログアウト、パスワード再設定 | 一部実装済み |
| 管理者認証 | `admins`と`AdminAuth`を使用した専用ログイン・ログアウト | 一部実装済み |
| イベント | 一覧、登録、詳細、編集、論理削除、ロゴ、カテゴリ、使用コート・利用時間 | 一部実装済み |
| 施設・コート | 管理者による管理と運営者による参照 | 一部実装済み |
| Application Service | 認証・アカウント、イベント作成、イベントロゴ | 一部導入済み |
| Policy / Domain Service | パスワード規則は一部実装済み。イベント認可はTable・Controllerによる暫定実装であり、操作別Policy、状態遷移、得点、スケジュール等は未実装 | 一部実装済み |
| 監査、通知キュー、WebSocket | 汎用基盤 | 未実装 |
| 選手、マーカー、ドロー、スケジュール、試合、結果 | 業務API | 未実装 |

一部のトランザクションと業務処理はControllerにも残っている。新規機能では本書の責務分担を適用し、既存処理は関連機能を変更する際に段階的にApplication Serviceへ移す。

## 基本方針

- CakePHPはJSON API、認証・認可、業務処理、永続化、監査および通知連携を担当する。
- Vue.js FRONT固有の表示状態やレイアウトをバックエンドへ持ち込まない。
- Controllerを薄く保ち、複数モデルにまたがる業務処理はApplication Serviceへ分ける。
- 業務ルールはPolicyまたはDomain Serviceへ分け、ControllerやTableへ重複させない。
- データ保存後の正式状態を基準とし、WebSocket通知やブラウザ内状態だけを正式な保存先にしない。
- 画面の表示・非表示に依存せず、入力検証と認可をAPIで必ず実施する。

## 責務

| 要素 | 主な責務 | 現在の状態 |
|---|---|---|
| API Controller | HTTP入力、認証結果、Service呼出し、HTTPレスポンス変換 | 実装済み。業務処理が残るControllerは段階的に整理 |
| Application Service | ユースケースの進行、トランザクション、複数モデルの調整 | 認証とイベントの一部で実装済み |
| Policy / Domain Service | 権限、状態遷移、得点、スケジュール等の業務ルール | パスワード規則を一部実装。その他は主に未実装 |
| Table | CakePHP ORMによる入力検証、永続化、関連、基本的な検索条件 | 実装済み |
| Repository / Persistence Port | ORMの詳細を隠す保存境界 | 導入要否を検討中 |
| Query Service | 一覧、大型表示、OBS等の読取処理 | 未実装 |
| Common Service | 監査、通知、時刻、言語、外部連携 | 認証メール等を一部実装済み |

EntityやTableへ画面専用の整形処理を置かない。単一テーブルの形式・必須・前後関係等はTableのValidator、複数集約や業務状態をまたぐ検査はApplication ServiceまたはPolicyで扱う。

## API処理の基本順序

1. 明示ルートとHTTPメソッドでリクエストを受け付ける。
2. Content-Type、本文サイズおよび入力形式を確認する。
3. 認証区分とセッションを確認する。
4. 入力値を許可項目に限定し、形式と業務上の整合性を検証する。
5. 対象イベント、ロール、担当範囲、所有者限定条件および現在状態を認可する。
6. Application Serviceが必要なトランザクション内で正式状態を保存する。
7. 成功、入力エラー、未認証、権限不足、競合等を共通形式のJSONへ変換する。
8. コミット後に必要な通知処理を開始する。

リクエストの未指定項目を自動的にEntityへ反映せず、操作ごとに受け付ける項目を明示する。公開、結果確定、訂正、権限変更等の重要操作は、汎用更新ではなく意図が分かるユースケースとして扱う。

### Cookie認証APIの保護

Cookieを使用する認証済みAPIには、次の保護をバックエンドの共通処理として適用する。画面側の入力制限やCORSレスポンスヘッダーだけを防御として扱わない。

1. `POST`、`PUT`、`PATCH`、`DELETE`等の状態変更APIでCSRF対策を必須とする。
2. ブラウザからの状態変更要求では`Origin`を検証し、許可リストと一致しないOriginをControllerへ到達させず拒否する。
3. JSONを受け付けるAPIは`Content-Type: application/json`に限定し、ファイルアップロード等で必要なエンドポイントだけ`multipart/form-data`を明示的に許可する。対応していない形式は`415 Unsupported Media Type`として拒否する。
4. リクエスト本文とアップロードファイルの上限をWebサーバー、PHPおよびCakePHPの共通処理で整合させ、エンドポイント固有の上限がある場合はさらに小さい値を適用する。具体的な共通上限値はインフラ条件と各入力仕様の確定後に決定する。
5. CSRFトークンの発行・送信・検証方法は検討中とし、方式の確定後に[認証・権限](104_authentication.md)、[フロントエンド](301_frontend.md)および[API](303_api.md)へ同じ契約を反映する。

現在はAPI全体をCakePHPのCSRF Middleware対象外としており、許可されていないOriginの明示的な拒否、JSON Content-Typeおよび本文サイズの共通検証も未実装である。

## トランザクション・同時更新・通知

1. API入力と認可をトランザクション開始前に可能な範囲で検証する。
2. トランザクション内で対象を再確認し、正式状態と必要な監査履歴を保存する。
3. メール送信、WebSocket送信等の外部I/Oをデータベーストランザクション内で実行しない。
4. コミット成功後に通知キューまたはWebSocket基盤へ更新を通知する。
5. 通知失敗時も保存済み状態を維持し、再送またはAPI再取得で回復する。

得点、試合開始、結果確定、訂正、スケジュール公開、問い合わせ返信等では、二重送信と同時更新を考慮する。状態バージョン、冪等性キー、行ロックまたは一意制約のどれを使用するかは操作ごとの競合条件に合わせて決定し、競合時は上書きせずAPIへ競合を返す。

「コミット後にその場で通知する」だけでは、保存成功直後のプロセス停止により通知が失われる可能性がある。メール通知は、業務データと送信ジョブを同じデータベーストランザクションで保存するTransactional Outbox方式を推奨案とする。現在の認証メールは同期送信であり、汎用通知キューとWebSocket通知は未実装である。

## 認証・認可

- 通常ユーザーと管理者の認証元、セッション内の認証情報および認証経路を分ける。
- CakePHP Authenticationは導入済みであり、通常ユーザーは`Auth`、管理者は`AdminAuth`を使用している。
- CakePHP Authorization等の認可ライブラリは未導入である。現在はTableの検索条件とControllerの判定による暫定実装であり、Policyによる操作別認可は未実装である。
- Controllerへ到達したことだけで認可済みとせず、対象イベント、ロール、担当範囲および操作条件を検証する。
- 公開API、通常ユーザーAPI、管理者APIの境界をルートと認可処理の両方で明確にする。
- Cookie、CORS、CSRF、セッション失効等の詳細は[認証・権限](104_authentication.md)を正本とする。
- 業務操作ごとの許可と追加条件は[権限マトリクス](../specifications/9000_common/9402_authorization_matrix.md)を正本とし、Policyと拒否系テストへ対応付ける。

イベントIDやユーザーIDをリクエストから受け取っただけで信頼しない。対象リソースを取得する検索条件にも認可範囲を適用し、別イベントのデータの存在や内容を不必要に公開しない。

### イベント単位の認可の実装範囲

2026年8月29日時点の実装範囲は次のとおりである。

| 項目 | 実装状態 |
|---|---|
| イベント作成 | メール確認済みの通常ユーザーが作成し、作成者をイベント所有者として登録する処理を実装済み |
| イベント一覧・詳細 | 所有者、または有効なイベントスタッフで`event_manager`ロールを持つ利用者に対象を限定する検索条件を実装済み |
| イベント編集・削除 | 所有者、または有効な`event_manager`であることの確認を実装済み |
| カテゴリ一覧・登録・編集・削除 | 対象イベントの所有者、または有効な`event_manager`であることの確認を実装済み |
| 担当範囲 | 開催日、コート、カテゴリ、時間帯等の範囲判定は未実装 |
| 操作別の追加条件 | イベント状態、試合状態、所有者限定操作、個人情報の項目制限、理由入力等は未実装 |
| 認可Policy | `EventPolicy`、`CategoryPolicy`等は未実装 |
| 拒否系テスト | 所有者・`event_manager`・無関係ユーザーの基本的な確認は一部実装済み。権限マトリクス全体との対応は未実施 |

現在の所有者・`event_manager`判定はイベント基本情報とカテゴリ管理の暫定認可であり、[権限マトリクス](../specifications/9000_common/9402_authorization_matrix.md)を満たす完成形ではない。対象機能を追加する際は、未実装の条件を理由に広く許可せず、操作別Policyと担当範囲の検査を追加する。

## 日時・タイムゾーン

- CakePHPの内部処理とMySQL接続セッションはUTCに統一する。
- 発生時刻、予定日時および実績日時はUTCへ変換して保存する。
- APIではUTCを示す`Z`またはUTCオフセットを含むISO 8601形式で日時を受け取り、検証後にUTCへ正規化する。
- `events.timezone`はIANAタイムゾーン名として検証する。オフセットを持たない現地日時をAPIで受け付ける必要が生じた場合は、タイムゾーンを同時に必須とし、存在しない時刻や夏時間により重複する時刻を検証する。
- 日付のみを表す`DATE`はUTC変換しない。
- システム時刻を直接取得する処理はテストで差し替え可能な境界へ集約することを候補とする。

現在のDocker Composeは`Asia/Tokyo`を使用しており、UTCへの統一と既存日時データの確認は未実施である。保存形式と移行方針は[データベース](201_database.md)、FRONTでの変換は[フロントエンド](301_frontend.md)を参照する。

## 入力・ファイル

- JSON、パスパラメータ、クエリ、アップロードをすべて未信頼入力として扱う。
- 必須、型、長さ、列挙値、日時の前後関係および関連データの存在をサーバー側で検証する。
- 一括代入では操作ごとの許可項目を限定し、所有者、権限、状態、監査項目等を利用者入力で変更させない。
- ファイルは容量、実内容、許可形式および画像としての妥当性を検査し、利用者が指定したファイル名を保存名に使用しない。
- アップロード先、公開方法、ウイルス検査、画像再生成、削除・バックアップとの整合は検討中とする。

イベントロゴは容量制限、許可MIMEタイプおよびランダムな保存名を実装済みだが、クライアント申告値だけに依存しない実内容検査と画像再生成は未実装である。

### ファイルとデータベースの整合性

ファイルとデータベースを単一のトランザクションで確定できないため、アップロードを伴う登録・更新では次の順序と補償処理を採用する。

1. 容量、実内容、許可形式および画像としての妥当性を検証し、新しいファイルを公開領域ではない一時領域へ保存する。
2. 一時ファイルの保存に成功した場合だけ、データベースの登録・更新を開始する。
3. データベース更新と新しいファイルの正式配置が完了した後に、置換対象の旧ファイルを削除する。
4. データベース更新または正式配置に失敗した場合は、新しく作成した一時ファイルおよび正式配置済みファイルを削除する補償処理を行い、旧ファイルと旧データを維持する。
5. イベント登録ではイベント本体と画像参照を一つのApplication Serviceで扱い、画像を含む要求に対してイベントだけを成功させない。全体を失敗として返し、作成済みイベントがある場合はデータベースをロールバックする。
6. 補償処理自体に失敗した場合は、利用者へ内部情報を返さず、追跡可能なエラーとして記録し、孤立ファイルの定期検出・削除対象とする。

現在のイベントロゴ処理はこの順序を満たしておらず、イベントまたは編集内容だけが保存される部分成功や、旧ファイルの先行削除が発生し得る。実装変更時には、正常系に加えて、一時保存失敗、DB保存失敗、正式配置失敗、旧ファイル削除失敗、補償処理失敗および再試行の異常系テストを追加する。

## エラーとログ

- 利用者へ返すエラーとサーバーログへ記録する内部情報を分離する。
- パスワード、トークン、Cookie、接続情報および不要な個人情報をログへ出力しない。
- 業務上の拒否、入力エラー、未認証、権限不足、対象なし、競合、レート制限およびサーバー障害をAPIで区別できるようにする。
- 監査履歴と技術ログを目的別に分ける。
- 技術ログの日時はUTCとし、環境、処理種別およびリクエストを追跡できる識別子を付ける方式を候補とする。
- 内部例外、SQL、スタックトレースおよび秘密情報を本番レスポンスへ含めない。

安定したAPIエラーコード、項目別エラー、リクエスト追跡IDおよびドメイン例外との対応は[API](303_api.md)と合わせて確定する。

### ログ等の保存期間案

次を初期案とし、個人情報保護方針、利用規約、障害調査に必要な期間および運用コストを確認して確定する。法令、契約または紛争対応による保全が必要なデータは、通常の削除処理から除外して個別に管理する。

| 対象 | 保存期間の初期案 | 理由・扱い |
|---|---:|---|
| デバッグログ | 30日 | 本番では必要最小限とし、秘密情報・個人情報を記録しない |
| アクセスログ・アプリケーション技術ログ | 90日 | 一般的な障害調査と不正アクセス調査に使用する |
| 認証・セキュリティ操作履歴 | 1年 | ログイン、停止、再設定、権限変更等の調査に使用する |
| イベント業務の監査履歴 | 3年 | 結果訂正、権限変更、問い合わせ返信等の説明責任に使用する |
| 成功した通知ジョブの実行履歴 | 90日 | 配信状況の問い合わせと短期的な障害調査に使用する。本文は原則として保持しない |
| 失敗・隔離した通知ジョブの履歴 | 1年 | 再送、原因分析および監査に使用する。不要な本文や宛先は早期に削除・マスキングする |

保存期間を過ぎたデータは定期処理で削除または匿名化し、バックアップから消えるまでの期間も別途定義する。監査履歴は更新・物理削除を通常の業務権限へ許可しない。

## 非同期処理

メール、外部通知、再送および重い集計は、公開や結果確定等の主要トランザクションから分離する。メール通知には次のTransactional Outbox構成を推奨する。採用の最終決定は、RSプランで利用できる定期実行または常駐処理を確認した後に行う。

1. 業務データ、認証用トークンおよび送信ジョブを同じデータベーストランザクションで保存する。
2. APIは送信完了を待たず、受付結果を返す。画面上は「送信を受け付けました」とし、SMTPの一時的な失敗を利用者へ内部エラーとして公開しない。
3. ワーカーが`pending`または`retry_wait`のジョブを取得し、SMTP送信後に`sent`へ変更する。処理中は`processing`とし、同一ジョブの多重実行を防ぐ。
4. 一時的な失敗は待機時間を段階的に延ばして再試行し、最大試行回数を超えたものは`failed`へ隔離する。初期案は1分後、5分後、30分後、2時間後、6時間後の最大5回とする。
5. ジョブには種類、対象ID、状態、試行回数、次回実行日時、最終エラー、冪等性キーおよび作成・送信日時を持たせる。メール本文や平文トークンをログへ残さない。
6. 確認・再設定URLに必要な秘密値をジョブへ保持する場合は、アプリケーション鍵で暗号化し、送信完了または保存期限到達後に削除する。暗号鍵はデータベースやGitへ保存しない。
7. 再送要求では新しい送信ジョブの保存と同じトランザクションで新しいトークンを発行し、旧トークンを無効化する。ジョブ保存に失敗した場合は旧トークンを維持する。
8. メール送信失敗によって、保存済みの公開状態、問い合わせ返信または結果を巻き戻さない。認証メールが最終失敗した場合は再送を受け付け、運用者が隔離ジョブを確認できるようにする。

キュー製品の採用要否、同時実行制御、監視・通知方法およびRSプラン上の起動方式は検討中である。専用キューを導入しない初期段階では、MySQLのOutboxテーブルを定期実行で処理する構成を候補とする。

## テスト・品質確認

- 業務ルールは単体テスト、APIはControllerまたは統合テストで確認する。
- 認証、権限、個人情報、ファイル、結果訂正およびオフライン競合には正常系と拒否系のテストを追加する。
- トランザクション失敗、通知失敗、二重要求、同時更新および状態競合を確認する。
- 日時はUTC変換、日付変更境界、夏時間開始・終了およびイベントタイムゾーンとの差異を確認する。
- マイグレーションと主要APIは、本番予定のMySQL 5.7との互換性を確認する。
- ファイルとDBの整合性では、一時保存、DB失敗、正式配置失敗、旧ファイル削除失敗、補償処理失敗および孤立ファイル回収を確認する。
- 通知では、送信待ち、再試行、最大試行回数超過、ワーカー停止・再開、二重実行および認証トークンとの整合性を確認する。

現在の`composer check`とCIはPHPUnitとPHP_CodeSnifferを実行する。PHPStanは開発依存関係と設定を持つが、`composer check`とCIには含まれていないため、静的解析を必須化するか検討中である。

本書は横断的なテスト方針を扱い、個別の前提条件、入力値、手順、期待結果および対応する要件・権限を記載するテスト仕様書は別途作成する。機能仕様、画面入力およびAPI契約が確定した機能からテストケースを追加し、権限マトリクスの各操作には許可・拒否の両方を対応付ける。
