# API

## 位置づけ

本書は、FRONTとCakePHPバックエンド間のHTTP/JSON APIに関する共通方針を定義する。個別エンドポイント、項目および権限表は実装前の詳細設計で確定する。

## 基本方針

- ベースパスは`/api/v1/...`とし、URLへメジャーバージョンを含める。
- JSONを入出力し、HTML画面の描画をAPIの責務に含めない。
- HTTPメソッドとルートを明示し、CakePHPの自動フォールバックルートへ依存しない。
- パブリック、通常ユーザー、管理者で認証・認可境界を分ける。
- APIはFRONTの画面構造ではなく、業務操作と参照目的に合わせて設計する。

## URLとHTTP

| 操作 | HTTPメソッドの基本 |
|---|---|
| 一覧・詳細取得 | `GET` |
| 新規登録 | `POST` |
| 全体更新 | `PUT` |
| 部分更新・状態操作 | `PATCH`または操作専用`POST`を詳細設計で選択 |
| 削除 | `DELETE`。論理削除等の業務ルールは個別に定義 |

状態変更を汎用的な更新へ押し込まず、結果確定、訂正、公開、競合解決等は意図が分かる操作として設計する。

## 認証・CORS・CSRF

- 本番APIは`https://api.squash-platform.com/api/v1/...`で提供する。
- Cookieベース認証を使用する場合、FRONTは資格情報を含めてAPIを呼び出す。
- CORSは`https://*.squash-platform.com`のような曖昧な許可ではなく、利用するオリジンを環境別に完全一致で列挙する。
- 通常ユーザーと管理者のCookie、セッションおよび認証ガードを分離する。
- CORSとは別にCSRF対策を適用する。
- 詳細は[認証・権限](104_authentication.md)を参照する。

## レスポンス

- 日時はタイムゾーンを判別できるISO 8601形式で返す。
- モニターやタイマー等、時刻補正が必要なレスポンスにはサーバー時刻を含める。
- 公開APIでは個人情報や内部管理項目を返さない。
- 一覧ではページング、絞り込み、並び順を明示する。
- 正式状態を更新するデータには、競合検出に使用できる状態バージョンを持たせる。

成功レスポンス、エラーレスポンス、ページングおよびフィールド名の共通形式は検討中であり、個別実装より先に決定する。

## エラー

少なくとも次をクライアントが区別できるようにする。

- 入力エラー
- 未認証
- 権限不足
- 対象なし
- 状態競合またはバージョン競合
- レート制限
- サーバー障害

内部例外、SQL、スタックトレース、認証情報をレスポンスへ含めない。画面表示用の日本語文言をAPIの固定仕様にせず、安定したエラーコードと項目情報を返す方式を候補とする。

## 冪等性と競合

- 得点操作やオフライン再送では、端末ID、操作ID、順序および状態バージョンにより重複登録を検出する。
- 同じ試合の複数端末競合を自動混在させず、正式記録の選択へ進める。
- 結果確定、決済、通知等の重複が重大な操作では冪等性キーの利用を詳細設計で検討する。

## リアルタイム通知

WebSocket通知には、少なくともイベント種別、対象ID、状態バージョンおよび発生日時を含める。通知受信後、必要に応じてAPIから最新状態を取得する。切断時はAPIポーリングへ切り替える。

## 検討中

- 共通レスポンスとエラー形式
- ページング方式
- APIごとの認証、権限、レート制限
- 更新APIの状態バージョンと冪等性キー
- OpenAPI等による機械可読なAPI定義
- WebSocket接続の認証と購読単位
