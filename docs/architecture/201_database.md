# データベース

## 位置づけ

本書は、Squash Platformで使用するデータベースの技術方針、環境分離、マイグレーション、トランザクションおよび運用上の扱いを定義する。エンティティ間の関係は[ER](202_er.md)、業務上の意味と集約は[データモデル](203_model.md)を参照する。

## データベース構成

| 項目 | 方針 | 状態 |
|---|---|---|
| DBMS | MySQL | 決定済み |
| 本番 | MySQL 5.7 | 2026年8月25日時点のRSプラン公式仕様。契約サーバーで要確認 |
| ローカル・CI | MySQL 8.4 LTS | 現在使用中。本番5.7との互換性確認が必要 |
| 文字コード | `utf8mb4` | 決定済み |
| 照合順序 | ローカルは`utf8mb4_0900_ai_ci` | 本番5.7で使用する値は検討中 |
| スキーマ変更 | CakePHP Migrations | 実装済み |
| 正式データ | APIで検証し、MySQLへ保存済みの状態 | 決定済み |
| 履歴 | 得点、結果訂正、権限、重要状態等の監査可能な履歴を保持 | 設計方針。対象機能は一部未実装 |

CakePHP 5.4はMySQL 5.7以上をサポートしているため、フレームワーク要件上はRSプランのMySQL 5.7を利用できる。ただし、現在のローカル環境とGitHub ActionsはMySQL 8.4であり、MySQL 5.7でのマイグレーション・テストは未実施である。本番接続前に、契約サーバーのバージョン、ポート、TLS、SQLモードおよび照合順序を確認する。

現在の`utf8mb4_0900_ai_ci`はMySQL 8系の照合順序であり、MySQL 5.7へそのまま適用しない。本番で使用する照合順序を確定した後、ローカル・CIとの差異をなくすか、MySQL 5.7互換試験を継続的に実行する。

- [CakePHP 5のシステム要件](https://book.cakephp.org/5.x/)
- [RSプランのデータベース仕様](https://help.onamae.com/answer/20165)

本番のホスト、データベース名、ユーザー名およびパスワード等の接続情報は、環境変数またはGit管理外の環境別設定で管理し、本書へ実値を記載しない。

## 現在の実装範囲

2026年8月25日時点では、CakePHP Migrationsで次の領域を実装している。

- ユーザー、管理者、選手、イベント、イベントスタッフ、固定ロール
- メール確認・パスワード再設定トークン、認証試行履歴
- 施設、コート、イベント使用コート・利用時間
- イベント基本情報、ロゴ等の表示情報、カテゴリ

試合、ドロー、スケジュール、得点・判定操作、正式記録、結果、オフライン分岐および監査履歴等は概念設計を含む未実装領域である。[ER](202_er.md)の全エンティティが物理テーブルとして実装済みという扱いにはしない。

現在のマイグレーションは一意制約と検索用インデックスを定義しているが、データベースの外部キー制約は定義していない。参照整合性をデータベース制約とアプリケーションのどちらで保証するか、削除・論理削除時の動作と合わせて詳細設計で確定する。

## 環境分離

- ローカル開発、ローカルテスト、CI、検証、本番で接続情報とデータベースを分離する。
- 本番認証情報をローカルDocker環境へ流用しない。
- `.env`、`config/app_local.php`、鍵および認証情報をGitへコミットしない。
- ローカルの接続方法と初期値は[ローカル開発環境](902_development.md)で管理する。

現在のDocker Composeでは`DATABASE_URL`と`DATABASE_TEST_URL`が同じデータベースを指しているため、ローカルテストにより開発データが削除される可能性がある。CIでは`snick_platform_test`を使用して分離済みだが、ローカルでもテスト専用データベースを用意するまでは、保持が必要な開発データに対して`composer test`または`composer check`を実行しない。

## マイグレーション

- テーブル、カラム、インデックス、制約等の変更は`app/config/Migrations/`のマイグレーションで管理する。
- 適用済みのマイグレーションを書き換えず、変更ごとに新しいマイグレーションを追加する。
- アプリケーションの展開とマイグレーションの順序を考慮し、原則として後方互換性のある段階的変更を行う。
- 本番適用前にMySQL 5.7相当の環境で全マイグレーションを先頭から適用し、ロールバック可能性と生成スキーマを確認する。
- 本番適用前にバックアップ、失敗時の復旧方法、所要時間およびロック影響を確認する。
- 本番マイグレーションの自動実行は、復旧手順が確定するまで無効とする。

## トランザクション

次は業務機能を実装する際の設計方針であり、得点・結果・監査履歴等は未実装である。

- 得点・判定、結果確定、結果訂正、権限変更等、一貫性が必要な操作をトランザクション境界として扱う。
- データ保存と監査履歴を同一トランザクションで確定できる設計を基本とする。
- WebSocket等の外部通知は、正式状態のコミット成功後に送信する。
- 通知失敗によって保存済みの正式状態を巻き戻さず、再通知またはAPI再取得で回復できるようにする。

## 履歴・削除

次はデータ保持に関する設計方針である。物理削除を禁止する対象と保存期間は、データ分類ごとに詳細設計で確定する。

- 重要な業務データは物理削除を避け、状態、履歴または論理削除で管理する。
- 結果訂正では確定済み記録を直接上書きせず、訂正履歴と変更理由を保持する。
- オフライン端末ごとの操作記録は競合解決まで独立して保持し、採用しなかった記録も監査用に残す。
- 個人情報、申込、試合結果、通知、監査履歴の具体的な保存期間は検討中とする。

## バックアップ・復旧

バックアップ・復旧は未構築である。バックアップ方式、対象、実行頻度、保持世代、保存先、暗号化、アクセス権、復旧目標および復旧試験を検討中とする。データベースだけでなく`webroot/uploads/`との整合も考慮する。方式を決定し、復旧試験に成功するまでは、本番マイグレーションを自動実行しない。

## 日時・タイムゾーン

日時はサーバーOSのタイムゾーンに依存させず、CakePHPの内部処理、MySQLの接続セッションおよびデータベースへの保存をUTCで統一する。

| 対象 | 保存・変換方針 | 状態 |
|---|---|---|
| 発生時刻 | 作成、更新、認証、送信、操作、監査等の時刻をUTCで保存する | 決定済み |
| 予定・実績日時 | イベント、コート利用、試合予定・実施等の日時をUTCで保存する | 決定済み |
| イベントのタイムゾーン | 開催地のIANAタイムゾーン名を`events.timezone`へ保持する | 決定済み |
| イベント作成時の初期値 | ブラウザのタイムゾーンを使用し、取得できない場合は`Asia/Tokyo`とする | 決定済み |
| 日付のみの値 | 生年月日や開催日等は`DATE`で保存し、UTC変換しない | 決定済み |

MySQLの`DATETIME`にはタイムゾーン情報が含まれず、自動変換も行われないため、CakePHPがUTCへ変換してから保存し、取得値をUTCとして解釈する。APIで日時を受け渡す場合は、UTCを示す`Z`または明示的なUTCオフセットを含むISO 8601形式を使用する。

イベントに関する日時の入力・表示は、保存済みの`events.timezone`へ変換する。ブラウザのタイムゾーンはイベント作成時の初期値に限定し、作成後に異なるタイムゾーンの端末からアクセスしてもイベント設定を自動変更しない。将来ユーザー別タイムゾーンを追加する場合は個人向け日時の表示に使用し、未設定時のみブラウザのタイムゾーンを使用する。システムログおよび監査ログはUTCを基準とする。

現在はCakePHPの基底設定とCIのデータベース接続がUTCである一方、Docker Composeのアプリケーション、MySQLおよびデータベース接続は`Asia/Tokyo`である。UTCへの設定変更と既存日時データへの影響確認は未実施であり、実装時に移行手順とテストを用意する。システム全体の方針は[システム構成](101_system-architecture.md)を参照する。

## 性能・インデックス

- 一意制約候補と検索要件は[ER](202_er.md)で管理する。
- イベント、開催日、コート、試合状態、公開版、更新日時等の検索条件を詳細設計時に確認する。
- インデックスは推測で固定せず、APIクエリと性能試験に基づいて決定する。
- 大型表示やOBS向けの読取負荷は、必要に応じてQuery Serviceや読取用投影で分離する。

## 検討中

- 契約サーバーのMySQLバージョン、照合順序、SQLモード、TLSおよびポート
- ローカル・CIを本番MySQL 5.7へ合わせるか、互換試験を追加するか
- ローカルテスト専用データベースの作成方法
- 外部キー制約と削除時動作の方針
- Docker ComposeのUTC化と既存日時データの移行・検証手順
- セッションをDBへ保存するかどうか
- バックアップ、リストア、Point-in-Time Recoveryの可否
- データ保存期間と匿名化・削除手順
- 通知キューおよびリアルタイム通知の永続化方式
