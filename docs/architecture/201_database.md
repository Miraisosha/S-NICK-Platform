# データベース

## 位置づけ

本書は、Squash Platformで使用するデータベースの技術方針、環境分離、マイグレーション、トランザクションおよび運用上の扱いを定義する。エンティティ間の関係は[ER](202_er.md)、業務上の意味と集約は[データモデル](203_model.md)を参照する。

## 決定済み

| 項目 | 方針 |
|---|---|
| DBMS | MySQL |
| 文字コード | `utf8mb4` |
| ローカル開発 | MySQL 8.4 LTS（2026年8月18日時点の暫定版） |
| スキーマ変更 | CakePHP Migrations |
| 正式データ | APIで検証し、MySQLへ保存済みの状態 |
| 履歴 | 得点、結果訂正、権限、重要状態等の監査可能な履歴を保持 |

本番MySQLのバージョン、ポート、TLS接続および照合順序は接続試験後に確定する。本番のホスト、データベース名、ユーザー名およびパスワード等の接続情報は、環境変数またはGit管理外の環境別設定で管理し、本書へ実値を記載しない。

## 環境分離

- ローカル、検証、本番で接続情報を分離する。
- 本番認証情報をローカルDocker環境へ流用しない。
- `.env`、`config/app_local.php`、鍵および認証情報をGitへコミットしない。
- ローカルの接続方法と初期値は[ローカル開発環境](902_development.md)で管理する。

## マイグレーション

- テーブル、カラム、インデックス、制約等の変更は`app/config/Migrations/`のマイグレーションで管理する。
- 適用済みのマイグレーションを書き換えず、変更ごとに新しいマイグレーションを追加する。
- アプリケーションの展開とマイグレーションの順序を考慮し、原則として後方互換性のある段階的変更を行う。
- 本番適用前にバックアップ、失敗時の復旧方法、所要時間およびロック影響を確認する。
- 本番マイグレーションの自動実行は、復旧手順が確定するまで無効とする。

## トランザクション

- 得点・判定、結果確定、結果訂正、権限変更等、一貫性が必要な操作をトランザクション境界として扱う。
- データ保存と監査履歴を同一トランザクションで確定できる設計を基本とする。
- WebSocket等の外部通知は、正式状態のコミット成功後に送信する。
- 通知失敗によって保存済みの正式状態を巻き戻さず、再通知またはAPI再取得で回復できるようにする。

## 履歴・削除

- 重要な業務データは物理削除を避け、状態、履歴または論理削除で管理する。
- 結果訂正では確定済み記録を直接上書きせず、訂正履歴と変更理由を保持する。
- オフライン端末ごとの操作記録は競合解決まで独立して保持し、採用しなかった記録も監査用に残す。
- 個人情報、申込、試合結果、通知、監査履歴の具体的な保存期間は検討中とする。

## バックアップ・復旧

バックアップ方式、保持世代、暗号化、復旧目標、復旧試験および本番マイグレーション前の取得方法は検討中である。方式を決定するまでは、本番マイグレーションを自動実行しない。

## 性能・インデックス

- 一意制約候補と検索要件は[ER](202_er.md)で管理する。
- イベント、開催日、コート、試合状態、公開版、更新日時等の検索条件を詳細設計時に確認する。
- インデックスは推測で固定せず、APIクエリと性能試験に基づいて決定する。
- 大型表示やOBS向けの読取負荷は、必要に応じてQuery Serviceや読取用投影で分離する。

## 検討中

- 本番MySQLのバージョン、照合順序、TLSおよびポート
- セッションをDBへ保存するかどうか
- バックアップ、リストア、Point-in-Time Recoveryの可否
- データ保存期間と匿名化・削除手順
- 通知キューおよびリアルタイム通知の永続化方式
