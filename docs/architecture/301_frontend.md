# フロントエンド構成

## 位置づけ

本書は、利用者別仕様に定義された画面の入口と主要な遷移を横断的に確認するための資料である。画面内の操作、試合状態および業務ルールの詳細は各仕様書を正本とする。

利用者区分ごとのViteエントリーと共通ソースの配置は[ディレクトリ構成](102_directory-structure.md)、APIとの通信規約は[API](303_api.md)を参照する。

- 確認時点：2026年8月29日
- 実線：決定済みの主要遷移
- 破線：後続フェーズ、または詳細が検討中の遷移
- `[F1]`、`[F2]`、`[F3]`：提供フェーズ
- 画面IDのない確認ダイアログは、遷移元画面の一部として扱う

実線・破線は設計の確定状態を表し、実装済みかどうかは表さない。実装状態は次の一覧で区別する。

各FRONTの配置と追加予定は[ディレクトリ構成](102_directory-structure.md)を参照する。決定済みの画面遷移が実装済みであるとは限らないため、実装着手時に対象機能の仕様書と現在のルートを確認する。

## Vue FRONTの基本構成

| 項目 | 方針 | 状態 |
|---|---|---|
| UIフレームワーク | Vue.js 3を使用する | 実装済み |
| 開発・ビルド | Viteを使用し、FRONTごとに開発サーバーとビルドを実行する | 実装済み |
| 画面遷移 | Vue RouterのHistoryモードを使用する | 実装済み |
| クライアント状態 | Piniaを使用し、認証状態等のアプリケーション共通状態を管理する | 実装済み |
| アプリ境界 | `operator`、`admin`等、利用者・用途別に独立したSPAとしてビルド・配備する | `operator`、`admin`を実装済み |
| API接続先 | `VITE_API_BASE_URL`から`/api/v1`の接続先を取得する | 実装済み |
| CSS | 新しいVue FRONTは独自CSSを使用し、Bootstrapへ依存しない | 決定済み・実装済み |

Bootstrap 5.3は、移行期間中に残るCakePHP HTML画面だけで使用する。新しいVue FRONTへBootstrapまたはVue向けBootstrapコンポーネントを無理に導入せず、共通CSSとVueコンポーネントでデザインを統一する。既存CakePHP画面を廃止した後、Bootstrap依存も削除対象として確認する。

### アプリと共通処理の分離

- 各FRONTは固有の`main.js`、ルート定義、画面および利用者別コンポーネントを持つ。
- APIクライアント、ルーター初期化、汎用アイコン等、業務的な意味が同じ処理だけを共通化する。
- 利用者区分によって業務ルールや認可条件が異なる処理を、見た目が似ていることだけを理由に共通化しない。
- Piniaは認証状態等のクライアント状態を保持するが、業務データの正式状態や認可判断の正本にはしない。
- ルートガードは未ログイン利用者の案内と画面遷移を担当する。権限の最終判定は各APIで行う。

### API通信・画面状態

- API通信は共通クライアントへ集約し、ベースURL、Cookie送信、JSON変換および共通エラー変換を画面ごとに重複実装しない。
- 認証状態は起動時にAPIへ照会し、ブラウザ内へ保存した表示状態だけでログイン済みと判定しない。
- 未認証、権限不足、入力エラー、競合、レート制限およびサーバー障害を区別し、[API](303_api.md)の共通エラーコードから画面表示へ変換する。
- API処理中は対象操作のローディング状態を表示し、送信ボタンの無効化等により意図しない二重送信を防止する。重要操作ではAPI側の冪等性も併用する。
- 画面を離れた後の古いレスポンスで表示を上書きしないよう、必要に応じてリクエストの取消またはレスポンスの世代管理を行う。
- 通信失敗時に自動再試行する操作と、利用者の確認を必要とする更新操作を分ける。状態変更を無条件に自動再送しない。

### ビルド成果物と環境別設定

- ビルド成果物は`frontend/dist/{app}/`へFRONT別に出力し、対応するサブドメインのドキュメントルートへ配備する。
- 開発、検証、本番で`VITE_API_BASE_URL`を分離し、ビルド時に対象環境を明示する。
- `VITE_`で始まる値はブラウザへ組み込まれる公開情報として扱い、パスワード、秘密鍵、API秘密情報等を設定しない。
- 環境別設定の必須項目が不足している場合は、誤った接続先で起動せず、ビルドまたは起動時に検出する。

## Cookie認証・CSRFにおけるFRONTの責務

- FRONTはCookieベースのセッション認証を使用し、API呼び出しでは資格情報を送信する。
- セッションCookieは`HttpOnly`を前提とし、FRONTのJavaScriptから読み取らない。セッションID、認証トークンおよびパスワードをLocal Storage、Session Storage、Piniaの永続化領域またはIndexedDBへ保存しない。
- 状態変更APIには、[認証・権限](104_authentication.md)で決定するCSRFトークンまたは同等の検証情報を共通APIクライアントから送信する。トークンの取得・更新方式はバックエンド方式の確定に合わせて決定する。
- CORSレスポンスヘッダーや`SameSite`属性だけをCSRF対策の完了として扱わない。
- ルートガードとメニュー非表示は利用者案内のための機能とし、認可済みであることの根拠にしない。
- ログイン後の戻り先は、現在のFRONT内に存在する相対パスだけを許可し、外部URLや別オリジンへ転送しない。
- APIから受け取った文字列および利用者入力をHTMLとして直接挿入しない。HTML表示が必要な機能は、許可要素と属性を限定して無害化する。
- メール確認・パスワード再設定用トークンをURLから取得した後は、処理に必要な値をメモリ上だけで保持し、ブラウザ履歴とアドレスバーから速やかに除去する。トークンをアクセス解析へ送信しない。
- セッション切れの場合は未保存内容の有無を確認してからログイン画面へ案内し、再認証後に安全に復帰できる画面だけ元の遷移先へ戻す。

### オフラインデータの保存方式

マーカー画面の操作履歴、試合状態、同期状態およびタイマー終了予定日時は、構造化データをトランザクション単位で保存できるIndexedDBを第一候補とする。IndexedDBのデータは通常のリロードやブラウザ再起動後も残るため、同じ端末・ブラウザから開始済み試合を復元できる。正式採用するライブラリ、データ構造および対応ブラウザは実装前に確定する。

| 保存先 | 保存対象 | 方針 |
|---|---|---|
| IndexedDB | 開始済み試合、操作履歴、未同期操作、状態バージョン、タイマー終了予定日時 | 推奨候補・未実装 |
| Cache Storage | HTML、JavaScript、CSS、フォント、アイコン、オフライン案内等のアプリ本体 | PWA導入時の候補・未実装 |
| Local Storage | 秘密性のない小容量の表示設定 | 必要最小限。試合データと認証情報には使用しない |
| Session Storage | 画面を閉じたら失われてもよい一時表示状態 | 試合復元には使用しない |

- 得点・判定等の操作は画面表示だけを先に更新せず、操作IDを付けてIndexedDBへ保存できたことを確認してから受付済みとして表示する。
- 1操作の履歴追加と試合状態更新は、途中でブラウザが終了しても片方だけ残らないよう、同じトランザクションで保存する。
- データは利用者、イベント、コート、試合および端末個体番号で区分し、別の利用者や大会のデータを誤って復元しない。
- 保存データへスキーマバージョンを持たせ、FRONT更新時は互換性を確認して移行する。移行できない場合に未同期データを黙って削除しない。
- 端末データは改ざん可能なものとして扱い、再接続時にAPIが権限、操作順序、重複、状態バージョンおよび競合を再検証する。
- 同期済みデータは直ちに削除せず、イベント終了後の保持期間を経て安全に削除する。具体的な保持期間は検討中とする。
- `navigator.storage.persist()`による永続ストレージ要求と、`navigator.storage.estimate()`による空き容量確認を行う候補とする。許可されない場合や容量不足時は警告し、新規試合を開始させない。
- プライベートブラウズでは終了時にデータが削除される可能性があるため、正式なマーカー運用では使用しない。
- 利用者によるサイトデータ削除、端末故障、ブラウザの保存領域破損までは防げない。オンライン時は速やかにAPIへ同期し、障害時は紙のマーカー用紙へ切り替えられるようにする。

### PWA構成の提案

オフライン継続とホーム画面からの起動が必要な`marker` FRONTを、最初のPWA対象とすることを推奨する。`operator`等の他FRONTへ適用する範囲は、必要性を確認して決定する。

1. Web App Manifest
   - `marker`専用の名称、アイコン、`start_url`、`scope`、表示モードおよびテーマ色を定義する。
   - QRコードから開いたイベント・コート等の業務情報をManifestへ固定せず、起動後に保存済み状態またはURLから解決する。
2. Service Worker
   - `marker`のスコープだけへ登録し、他のFRONTやAPI通信を意図せず制御しない。
   - API更新リクエストをキャッシュで成功したように見せず、未同期操作はIndexedDBと同期処理で管理する。
3. キャッシュ範囲
   - バージョン付きのHTML、JavaScript、CSS、フォント、アイコンおよびオフライン案内をアプリシェルとして保存する。
   - 認証済みAPIレスポンスや個人情報をCache Storageへ無差別に保存しない。復元に必要な業務データはIndexedDBで項目を限定して管理する。
4. 新バージョンへの更新
   - 新しいService Workerを検出しても、進行中または未同期の試合がある間は強制的に画面を再読込しない。
   - 更新可能であることを表示し、未同期操作の解消後または試合終了後に利用者の確認を得て切り替える。
   - キャッシュ名へFRONTのバージョンを含め、新版の有効化後に不要な旧キャッシュを削除する。
5. API互換性
   - `/api/v1`内では、開催中イベントで使用される旧FRONTを直ちに動作不能にする破壊的変更を行わない。
   - 互換性を失う変更は新しいAPIバージョンで提供するか、FRONTの更新完了を確認できる移行期間を設ける。
   - FRONTのビルドバージョンをAPIへ送信し、非対応バージョンには同期前に明確な更新案内を返す方式を候補とする。
6. オフラインで開始・継続できる範囲
   - オフラインで継続できるのは、オンライン中に権限確認と必要データ取得を完了し、端末へ保存済みの開始済み試合だけとする。
   - 新規試合開始、担当変更、強制引継ぎ、結果の正式確定等、サーバーとの排他制御が必要な操作はオンライン時だけ許可する。
7. キャッシュ・保存領域の復旧
   - 起動時にキャッシュ、IndexedDBのスキーマおよび未同期件数を検査し、異常時は復旧画面を表示する。
   - アプリ本体のキャッシュだけを削除・再取得する操作と、未同期の業務データを削除する操作を分離する。
   - 未同期データの削除は確認なしに実行せず、可能な場合は診断情報または復旧用データとして退避する。具体的な退避形式は検討中とする。

PWA、IndexedDBおよび永続ストレージは、ブラウザによる保存を補助する仕組みであり、端末故障や利用者によるデータ消去を含む完全な保存保証ではない。この制約を画面と運用手順の両方へ明記する。

## 日時・タイムゾーン

CakePHP、MySQL接続およびデータベースへ保存する日時はUTCを基準とする。FRONTはAPIから受け取ったUTC日時を用途に応じたタイムゾーンへ変換し、入力値はUTCへ変換してからAPIへ送信する。APIの日時形式は[API](303_api.md)、保存方針は[データベース](201_database.md)を参照する。

| 場面 | FRONTの扱い | 状態 |
|---|---|---|
| イベント作成 | ブラウザのIANAタイムゾーンを初期値として表示し、運営者が確認・変更できるようにする | 決定済み |
| ブラウザから取得できない場合 | `Asia/Tokyo`を初期値とする | 決定済み |
| イベント作成後 | `events.timezone`を基準にイベント日時を入力・表示する | 決定済み |
| 異なる地域からのアクセス | ブラウザのタイムゾーンで`events.timezone`を自動変更しない | 決定済み |
| 個人向け日時 | 将来ユーザー設定を追加した場合はその設定を優先し、未設定時はブラウザのタイムゾーンを使用する | 将来対応 |
| システムログ・監査日時 | UTCとして扱う | 決定済み |
| 日付のみの値 | 生年月日や開催日等はUTC変換しない | 決定済み |

ブラウザのタイムゾーン取得には`Intl.DateTimeFormat().resolvedOptions().timeZone`を使用できるが、取得値を確定値として黙って保存せず、イベント作成画面へ表示する。`datetime-local`はタイムゾーンを保持しないため、イベント日時の入力値は`events.timezone`の現地日時として解釈してUTCへ変換する。表示には必要に応じて`JST`等の略称または`Asia/Tokyo`等のタイムゾーン名を併記し、夏時間を固定オフセットで処理しない。

現在のイベント登録・編集画面には、イベントタイムゾーンの確認・変更と、UTCとの明示的な相互変換が未実装である。実装時は、日付をまたぐ変換、夏時間の開始・終了境界、ブラウザとイベントのタイムゾーンが異なる場合をテストする。

## UIデザインの目的

Squash Platformの全画面について、操作性と視認性を最優先にしながら、清潔感があり、丸みを帯びた優しい印象へ統一する。本書はパブリック、運営者、マーカー、選手および管理者画面に共通するデザイン方針を定める。

マーカー、大型得点ボードおよびOBS等、用途固有の優先順位がある画面は各仕様書を優先し、色、文字、余白、操作部品の基本的な考え方は本書を参照する。

## 決定済みのデザイン方針

### 優先順位

1. 操作対象と現在状態を迷わず判別できること
2. 誤操作を防ぎ、主要操作を少ない手順で実行できること
3. PCでも文字とボタンを過度に小さくしないこと
4. 十分な余白、角丸、穏やかな配色により清潔感と親しみやすさを表現すること
5. Squash Platformとして一貫した配色を使用し、提供元であるS-NICKの表示へ依存しないこと

情報量を増やすために文字、行間またはボタンを極端に小さくしない。画面へ収まらない場合は、情報のグループ化、段階表示、タブ、絞込みおよび適切なスクロールを使用する。

### 画面全体の印象

- 背景は白またはわずかに暖かい明色を基本とする。
- カード、入力欄、ダイアログおよびボタンへ統一した角丸を使用する。
- 枠線と影は弱くし、太い黒枠や強い立体表現を常用しない。
- 重要度は色の多用ではなく、文字サイズ、余白、配置および面の濃淡で表現する。
- 1画面で使用する強いアクセント色を絞り、落ち着いた運営画面を維持する。

## UIカラーパレット

添付されたキャラクター`Pattern1.png`から抽出した代表色を、Squash Platformの初期UIカラーパレットとして参考利用する。配色を使用する場合もS-NICKの名称、ロゴまたはキャラクターを併記する必要はない。正式なシステムカラーが別途定められた場合は、その値へ置き換える。

| 用途 | 初期基準色 | 使用方針 |
|---|---|---|
| メインイエロー | `#FED258` | 選択状態、見出しの一部、穏やかな強調面。文字色には濃茶を使用する |
| メインブラウン | `#572C00` | 主要文字、主要操作、見出し等 |
| アクセントピンク | `#FF008F` | 注目させる小さなアクセントへ限定し、広い背景面には常用しない |
| アクセントブルー | `#00A6FF` | リンク、補助的な選択状態、情報表示等 |
| 基本背景 | `#FFFCF5` | 画面背景の候補。純白のカードと組み合わせる |
| 基本文字 | `#2E261F` | 本文と主要情報。真黒より柔らかいが十分な可読性を確保する |
| 境界線 | `#E7DED1` | カード、表、入力欄等の控えめな区切り |

- メインイエロー上には濃い文字を使用し、白文字を基本としない。
- ピンクと青は補助的なアクセントとし、同じ画面内で大面積に競合させない。
- 成功、警告、エラー、情報等の状態色は意味を優先し、メインカラーだけで代用しない。
- 色だけで状態や操作可否を伝えず、文字、アイコン、形またはラベルを併用する。
- 実装前に通常、ホバー、フォーカス、無効、選択およびエラー状態の文字コントラストを確認する。

## 文字と操作部品

以下は初期レイアウト作成時の推奨値とし、主要画面のプロトタイプと実機確認後に確定する。

| 対象 | PCでの推奨値 | タッチ端末での推奨値 |
|---|---:|---:|
| 本文 | 16～18 CSS px | 17～20 CSS px |
| 入力欄・ボタン文字 | 16～18 CSS px | 18 CSS px以上 |
| 画面タイトル | 28～32 CSS px | 26～32 CSS px |
| セクション見出し | 20～24 CSS px | 20～24 CSS px |
| 補助情報 | 14～16 CSS px | 15～16 CSS px |
| 主要ボタン高さ | 48 CSS px以上 | 56 CSS px以上 |
| 表・一覧の標準行高 | 48～56 CSS px | 52～60 CSS px |

- PC画面でも、主要ボタンを小さなテキストリンクやアイコンだけの操作へ置き換えない。
- 頻繁に使う主要操作は、画面右上だけでなく対象情報の近くへ配置する。
- アイコンだけでは意味が伝わりにくい操作には、短い文字ラベルを付ける。
- 破壊的操作と通常操作を隣接させる場合は、間隔、色および確認手順で誤操作を防止する。
- キーボードフォーカスを明確に表示し、フォーカス枠をデザイン上の理由だけで消さない。
- 試合一覧の行・カードから詳細へ移動する場合は、行・カード全体をリンクとしてクリック・タップ・キーボード操作できるようにし、重複する「詳細」ボタンを設置しない。
- 対戦選手を1行で示す場合は`Player A vs Player B`形式に統一し、言語にかかわらず区切りへ`vs`を使用する。

## 角丸・余白・レイアウト

- 基本間隔は8 CSS pxの倍数を基準とし、関連要素は近く、異なるグループは広く離す。
- ボタンと入力欄の角丸は10～14 CSS px、カードとダイアログは14～20 CSS pxを初期候補とする。
- 状態ラベル等を除き、すべての部品を完全なカプセル形状にはしない。
- PCでは内容幅を無制限に広げず、読み物・入力フォーム・一覧等の用途に応じて最大幅を設ける。
- 一覧画面は余白を確保しつつ、検索、絞込み、主要操作、一覧結果の順序を画面間で統一する。
- レスポンシブ表示では情報の優先順位を維持し、画面幅だけを理由に主要操作を隠さない。

## 提供元・キャラクターの使用方針

通常画面ではSquash Platform、イベント、大会主催者、選手および競技情報を主役とし、S-NICKの名称、ロゴまたはキャラクターを前面に出さない。提供元は法人名で控えめに表示する。

### 控えめに表示できる場所

- 日本語画面のフッターに表示する`提供：株式会社未来創社`
- 英語画面のフッターに表示する`Provided by Miraisosha Co., Ltd.`。正式な英文商号の確認後に確定する
- 提供元情報、利用規約、プライバシーポリシー、問い合わせ先
- マニュアルの提供元・著作権情報
- S-NICK自体を説明する専用ページ

### 表示しない場所

- 通常画面の共通ヘッダー、メインナビゲーションおよびページタイトル
- ログイン画面の主見出し、初回案内、空表示および操作完了表示
- 運営者・マーカーの主要操作領域
- 得点、試合状態、警告または重要な確認ダイアログの背景
- 大型得点ボード、OBSオーバーレイおよび大会の観客向け表示
- イベント主催者や選手の情報より目立つ位置
- 全画面背景、大きな透かし、常時表示される大型イラスト

通常画面ではキャラクターを表示しない。提供元情報等の限定された場所で使用する場合も、本文やSquash Platformの名称より目立たない寸法とし、キャラクターがなくても情報、操作性および画面デザインが成立する構成とする。

### フッター表示

- 提供元表記は12～13 CSS px程度の補助文字とし、本文より弱いグレーを使用する。
- ロゴ、キャラクター、背景色および装飾枠を付けず、文字だけで表示する。
- PCとタブレットでは画面またはコンテンツ領域の右下、スマートフォンでは主要内容と下部ナビゲーションの間を基本位置とする。
- 主要操作に追従する固定表示にはせず、スクロール末尾または画面フッターとして表示する。
- 大型得点ボード、OBSオーバーレイおよび大会主催者が使用する会場表示には表示しない。

## 画面種別ごとの適用

| 画面種別 | 適用方針 |
|---|---|
| パブリック | イベントや選手を主役とし、明るく読みやすいカードと大きめの導線を使用する |
| 運営者 | PCを主用途としながら、緊急時にはタブレット・スマートフォンでも主要操作を継続できる構成とする。多数の項目を扱う場合も文字・行高を確保する |
| マーカー | 本書よりもさらに大きなタップ領域を使用し、得点と判定の操作性を最優先する |
| 選手 | スマートフォンを優先し、申込状態、支払状態、次の予定を大きく表示する |
| 管理者 | 情報密度を確保しつつ、PCでも小さすぎる表、ボタン、入力欄を使用しない |
| 大型表示・OBS | 競技情報とスポンサーを主役とし、キャラクターを表示しない |

## アクセシビリティ

全FRONTはWCAG 2.2のレベルAAを目標とする。マーカー、大型表示およびOBS等の用途固有画面にも、適用可能な達成基準を適用する。

1. キーボード操作
   - 主要機能をキーボードだけで実行できるようにし、フォーカスが抜けられない状態を作らない。
   - 行やカード全体を操作対象にする場合も、適切なリンクまたはボタンとしてフォーカス・実行できるようにする。
2. 入力エラー
   - エラー内容を項目の近くに文字で表示し、`label`、説明およびエラーをプログラム上も関連付ける。
   - 色だけでエラーを示さず、画面上部の概要から該当項目へ移動できるようにする。
3. ダイアログのフォーカス
   - 開いた時にダイアログ内へフォーカスを移し、背後へフォーカスが移動しないようにする。
   - 閉じた時は原則として起動元へフォーカスを戻し、Escキー等の閉じ方を提供する。ただし、処理中で閉じられない場合は理由を示す。
4. 読み上げ通知
   - 保存成功、通信切断、再接続、入力エラー、競合およびタイマー終了等の重要な状態変化を、画面表示に加えて適切なライブリージョンで通知する。
   - 頻繁な自動更新をすべて読み上げず、操作判断に必要な変化へ限定する。
5. 拡大・リフロー
   - 文字を200%へ拡大しても、主要情報や操作が欠落・重複・重なりを起こさないようにする。
   - 固定ヘッダーや下部ナビゲーションが、拡大時のフォーカス対象を隠さないようにする。
6. 動きの軽減
   - `prefers-reduced-motion`を尊重し、装飾アニメーション、自動スクロールおよび点滅を停止または簡略化する。
   - 得点・警告等の意味をアニメーションだけで伝えない。
7. 最小操作領域
   - WCAG 2.2 AAの最小基準を満たしたうえで、タッチ端末の独立した主要操作は原則44×44 CSS px以上とする。
   - マーカー画面の得点・判定等、頻繁または誤操作の影響が大きい操作は、既定の主要ボタン高さ56 CSS px以上を優先する。

## フロントエンドのテスト方針

採用するテストツールとCIでの実行方法は検討中とするが、少なくとも次の範囲を自動テストと実機確認の対象にする。

1. コンポーネント・単体テスト
   - 共通部品、Piniaストア、ルートガード、APIエラー変換、日時変換およびオフライン同期ロジックを確認する。
2. 主要画面のE2Eテスト
   - 登録、ログイン、イベント作成、マーカー起動、得点入力、結果確定等の主要導線をブラウザ上で確認する。
3. 認証・権限・セッション切れ
   - 未認証、権限不足、別イベントへのアクセス、セッション切れ、全端末失効およびログイン後の安全な復帰を確認する。
4. オフライン・再接続・競合
   - 通信切断、リロード、ブラウザ再起動、未同期操作の再送、重複送信、別端末との分岐および保存容量不足を確認する。
5. タイムゾーンと夏時間
   - 日付をまたぐ変換、夏時間の存在しない時刻・重複する時刻、ブラウザとイベントのタイムゾーンが異なる場合を確認する。
6. 端末・画面幅
   - PC、10インチ前後、12インチ前後、スマートフォンの代表的な画面幅と、縦向き・横向きを確認する。
   - マーカーで正式対応するブラウザとOSの組合せは実装前に確定し、実機でオフライン復元を確認する。
7. アクセシビリティ
   - 自動検査に加え、キーボード操作、スクリーンリーダー、200%拡大、色に依存しない判別およびタップ領域を手動確認する。

テスト失敗を見逃さないよう、実装開始後はビルド、静的解析、単体・コンポーネントテストおよび主要E2EテストをCIへ組み込む。すべての端末差や読み上げを自動検査だけで保証できないため、リリース前の実機・手動確認を併用する。

## 運営者画面の初期デザイン案

以下は、運営者が大会当日の状況を確認するダッシュボードを例にした初期デザイン案である。画面構成、情報の優先順位、レスポンシブ時の変形および共通部品の方向性を確認するための資料とし、各項目、件数、文言および遷移先は画面ごとの詳細設計で調整する。

### PCブラウザ

![運営者ダッシュボードのPC版デザイン案](../specifications/images/operator/operator-dashboard-desktop.svg)

- 左側へ主要機能のナビゲーション、上部へイベント選択と利用者情報を配置する。
- 画面上部で大会状態と対応件数を把握し、その下で現在・次の試合と警告を確認する。
- 試合一覧は行全体をクリック・タップすると詳細へ遷移する。「詳細」ボタンは設置せず、ホバー、フォーカスおよび右端の矢印で遷移可能であることを示す。
- 対戦選手は`Player A vs Player B`形式で表示し、`対`は使用しない。

- 画面下部へ装飾のない補助文字で`提供：株式会社未来創社`を表示する。

### タブレット・スマートフォン

![運営者ダッシュボードのタブレット・スマートフォン版デザイン案](../specifications/images/operator/operator-dashboard-responsive.svg)

- タブレットでは主要一覧と警告・クイック操作を2列で表示し、メニューを上部へ集約する。
