# 600 共通基盤

## 610 API

- Web画面、表示端末、OBS連携で一貫したデータを利用する。
- 認証、認可、エラー形式、バージョニングは詳細設計で定義する。
- 時刻に依存するモニター用APIレスポンスには、レスポンス生成時点のSquash Platformサーバー時刻をタイムゾーン判別可能なISO 8601形式で含める。
- 表示端末はサーバー時刻を正として端末時計との差を補正し、定期更新と通信復旧時に再同期する。
- 試合の遅延は、未開始のまま現在有効な開始予定時刻から5分以上経過した時点で判定し、運営画面、パブリック画面、モニターで同じ判定結果を使用する。

## 620 データベース

- イベント、カテゴリ、エントリー、選手、試合、ゲーム、得点履歴、コート、配信、スポンサー等を管理する。
- 重要状態は履歴を保持し、公開用データと個人情報を分離する。
- 本番MySQLはホスト `mysql18.onamae.ne.jp`、データベース名・ユーザー名 `492th_snick_platform`、文字コード `utf8mb4` を使用する。
- データベースパスワードは環境変数またはGit管理外設定から取得し、設計書、ログ、Gitへ保存しない。
- 照合順序、接続ポート、TLS接続の可否は本番環境で確認して決定する。

## 630 リアルタイム同期

- マーカー入力を大型表示、観客画面、OBSへ反映する。
- 310 コート別試合一覧は、公開済みスケジュール、コート変更、選手、棄権、試合状態、結果の変更をページ再読込なしで反映する。
- 得点・判定等の更新要求はHTTPS APIへJSONで送信し、サーバーで保存した状態を正式状態とする。WebSocketは保存済み状態の更新通知に使用する。
- WebSocket通知のデータ形式はJSONとし、少なくともイベント種別、対象ID、状態バージョンおよび発生日時を含める。
- 通常時の更新方式はWebSocketによるサーバー通知とする。WebSocketが切断された場合は自動再接続を行い、再接続までの間はAPIポーリングへ自動的に切り替える。
- WebSocket再接続時は最新状態をAPIで再取得してから通知受信を再開し、切断中の更新漏れを補完する。APIポーリングの間隔は設定可能とし、初期値は性能試験と会場ネットワーク試験で決定する。
- 再接続時はイベントIDと状態バージョンにより、重複イベントおよび順序逆転を検出する。
- 同一試合のオフライン操作が複数端末へ分岐した場合は、端末ごとの操作履歴を独立して保持し、自動統合や時刻順での混在を行わない。権限を持つ運営者が正式な1つの記録を選択する。

## 640 認証・権限

- 運営者、スタッフ、マーカー、選手等の通常ユーザーは、共通アカウントとイベント単位の役割を組み合わせる。
- 通常ユーザーのログインには確認済みメールアドレスを使用し、内部ユーザーIDと変更不可のアカウント番号を自動生成する。アカウント番号はログインには使用しない。
- プラットフォーム管理者は`admins`テーブル、`/admin/login`、管理者専用認証ガードおよび管理者専用セッションを使用し、通常ユーザーの`users`テーブルと認証経路を分離する。
- 管理者用Cookie、自動ログインおよびパスワード再設定は通常ユーザーと共有しない。
- パスワードはArgon2idでハッシュ化し、平文や復号可能な形式で保存しない。
- パスワードは6～64文字とし、Argon2idの負荷パラメータはCakePHPの環境別設定から変更できるようにする。
- パスワード登録・変更・再設定時は、一般的・既知漏えい・推測容易なパスワードを禁止リストで照合する。
- 5回連続失敗で30分停止し、停止中に同じアカウントへの認証がさらに失敗した場合は、その時点から30分後まで停止期限を延長する。接続元レート制限を併用する。
- 確認・パスワード再設定トークンは本体を保存せず、SHA-256ハッシュを保存する。
- 自動ログインの有効期間は30日とし、パスワード再設定時は全端末セッションを無効化する。
- 同一アカウントで最大5件の端末セッションを有効にでき、6件目では利用者が既存セッションを1件解除してからログインする。
- 同一ブラウザの複数タブは1件とし、別ブラウザやCookieを共有しないプロファイルは別セッションとして扱う。
- 利用者による個別セッション解除と全端末ログアウトを提供する。
- セッション一覧には取得可能な端末種別、OS、ブラウザ、初回ログイン、最終利用、IPアドレス、IP由来の概算地域、現在端末、自動ログイン状態を表示する。GPSや永続的な端末指紋はこの目的だけには取得しない。
- 通常セッションの無操作タイムアウトは9時間とする。最大継続時間は検討中とする。
- 二要素認証は導入方針とするが、端末種別だけで適用を免除しない。スマートフォン・タブレットの入力軽減には、初回確認後の取消可能な信頼済み端末方式を候補とする。
- 退会画面は運営者向けユーザー設定と選手画面の両方から共通機能として利用できるようにし、管理者は別の利用停止機能を使用する。
- 退会アカウントは論理削除し、過去の申込、試合結果、操作履歴は大会記録・監査履歴として保持する。具体的な保存期間と再登録方法は将来検討とする。

## 650 通知

- 本仕様でいう「通知」は、スケジュール変更等の業務メッセージとその送信処理を指す。SMTPは初期通知をメールで届けるための送信手段であり、Webプッシュ通知やLINEは将来追加する別の通知手段として区別する。
- 初期通知は、お名前.comのSMTPサーバー `mail71.onamae.ne.jp`、ポート465、SSL/TLS、送信元 `info@s-nick.com` を使用する。
- SMTPパスワードは環境変数またはGit管理外設定から取得し、設計書、ログ、Gitへ保存しない。
- フェーズ2の試合当日スケジュール変更通知は、選手の確認済みメールアドレスへ受信者ごとに個別送信する。
- スケジュールの下書き編集時には送信せず、変更版の公開を通知イベントとして扱う。
- 同一公開操作内の重複通知をまとめ、同じ選手・同じ試合へ同内容を重複送信しない。
- メール送信はキューで処理し、公開処理と分離する。送信失敗時も公開済みスケジュールは維持し、運営者が失敗を確認・再送できるようにする。
- SMTP接続タイムアウトと再試行はCakePHPの環境別設定として実装時に定義し、SPF、DKIM、DMARCはメールサーバー・DNS側で設定する。
- 通知種別、対象イベント、対象試合、対象利用者、通知手段、宛先、本文、送信者、作成日時、送信日時、送信結果、失敗理由を記録する。
- 将来の通知手段としてWebプッシュ通知とLINE等のメッセージ通知を追加できるよう、メール固有処理と通知内容を分離する。
- 外部通知サービスの認証情報、アクセストークン等は環境変数またはGit管理外の秘密情報として扱う。
- Webプッシュ通知やLINE等は本人の利用開始・連携・解除を前提とし、具体的なサービス、アカウント連携方式、メールとの優先順位、同時送信、通知設定は検討中とする。

## 660 共通UI

- タブレット、PC、大型モニターで目的に応じた表示を提供する。
- PC画面でも文字、入力欄、表の行および主要ボタンを大きめにし、情報密度だけを理由に操作対象を小さくしない。
- 運営者画面はPCブラウザを主用途とするが、緊急時にタブレット・スマートフォンから主要操作を継続できるレスポンシブ表示とする。
- 清潔感のある明るい背景、十分な余白、統一した角丸および控えめな影を使用し、優しい印象へ統一する。
- 添付キャラクターから抽出した黄と茶をUI配色の参考として使用し、ピンクと青は限定的なアクセントとする。配色はS-NICKの表示を伴わず、Squash Platformの画面デザインとして使用する。
- S-NICKの名称、ロゴおよびキャラクターは通常画面のヘッダーや主要操作へ配置しない。提供元表示は日本語画面で`提供：株式会社未来創社`、英語画面で`Provided by Miraisosha Co., Ltd.`を初期値とし、フッター、提供元情報、規約、問い合わせ先等へ控えめに表示する。大型得点ボードとOBSには提供元表示を出さない。英語表記は正式な英文商号の確認後に確定する。
- 対戦選手を1行で表示する場合は、全画面で`Player A vs Player B`形式に統一する。
- マーカー画面はフェーズ3で日本語、英語、韓国語へ対応する。縦横レイアウト、文字サイズ、タップ領域等の詳細は [マーカー仕様](300_Marker.md) を参照する。
- マーカー以外の画面における多言語対応と、システム全体のアクセシビリティ対象範囲は検討中とする。

配色、文字、操作部品、角丸、余白およびキャラクターの詳細は [Squash Platform UIデザインガイド](UiDesignGuide.md) を参照する。

## 670 配信・ネットワーク

- 映像系統は GoPro → HDMI → ワイヤレスHDMI → キャプチャ → OBS → YouTube Live を基本候補とする。
- OBS PCは有線LAN、表示タブレットはWi-Fiを基本とする。
- LTE/5GルーターはデュアルSIMの切替型フェイルオーバーを基本候補とし、回線ボンディングとは区別する。
- コートごとにYouTube配信枠、OBS設定、公開視聴URL、オーバーレイURLを分離する。
- ストリームキーは秘密情報とし、公開用データ、ログ、Gitへ保存しない。
- 詳細は [ライブ配信設計](../04_live-streaming.md) と [ネットワーク・機材](../05_network-and-hardware.md) を参照する。

## 680 マニュアル・問い合わせ・QA

**導入時期：フェーズ4**

### 決定済み

- Squash Platformの操作マニュアルをフェーズ4で作成する。
- マニュアルは実際の画面と権限に対応させ、仕様変更時に内容を更新できる構成とする。

### 候補

- 利用者がログイン中の画面や対象イベントを引き継いで質問できる問い合わせフォーム
- 質問、回答、カテゴリ、対象機能、検索用キーワード等を登録し、利用者が検索できるQA機能
- 問い合わせへの回答から、個人情報やイベント固有情報を除外して一般公開可能なQAを作成する運用
- 入力中に既存QAの候補を表示し、同じ問い合わせを減らす仕組み

### 検討中

- マニュアルの対象利用者、章構成、HTML・PDF・動画等の提供形式、言語、版管理および公開単位
- 問い合わせフォームを利用できる利用者と、未ログイン利用者からの受付可否
- 問い合わせ種別、必須項目、ファイル添付、受付番号、優先度、担当割当、対応状態および回答期限
- 受付・回答通知を画面、メールまたは将来の外部通知のどれで行うか
- QAの公開範囲、公開前承認、検索方式、並び順、同義語、表記揺れおよび検索結果がない場合の導線
- 問い合わせ本文、添付ファイル、操作状況、個人情報および回答履歴の保存期間と閲覧権限
- 問い合わせ管理とQA編集をSquash Platform内で構築するか、外部サービスと連携するか

問い合わせフォームとQA検索はフェーズ4の候補であり、上記の検討事項を確定するまでは実装範囲に含めない。
